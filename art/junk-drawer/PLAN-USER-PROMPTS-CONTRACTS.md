## C1. Endpoints

Two new endpoints, `api/jd-generate.php` and `api/jd-rate.php`. Both:

- **POST only** (`405` + `{"ok":false,"error":{"code":"method_not_allowed"}}`
  otherwise). `OPTIONS` is answered by the shared origin helper (below)
  with `204` before anything else runs.
- `Content-Type: application/json` on every response, including errors.
- **Origin enforcement**: first statement after the includes is
  `jd_require_allowed_origin();` (C1.1). No other file may emit CORS
  headers.
- No `session_start()`, no `setcookie()`, no cookie reads. Any
  client-held identifier travels in the JSON body.
- All timestamps written by PHP as `gmdate('Y-m-d H:i:s')` (UTC).
- IDs are 26-char ULIDs generated by `jd_ulid()` in `api/jd-config.php`
  (Crockford base32, `random_bytes`-backed). Unguessable-enough that
  possession of a `submission_id` is the capability to rate it.

### C1.1 Shared origin helper — `api/jd-origin.php`

```php
const JD_ALLOWED_ORIGINS = [
    'https://municipalsky.com',
    'https://www.municipalsky.com',
    // 'capacitor://localhost',   // app stage: uncomment, one-line edit
];
function jd_require_allowed_origin(): void { ... }
```

Behavior (APP §4.2, verbatim intent):

1. If `JD_DEV_MODE` (C6) is true, `http://localhost:8000` and
   `http://127.0.0.1:8000` are appended to the allowlist at runtime.
2. If method is `OPTIONS`: respond `204` with
   `Access-Control-Allow-Origin: <matched origin>` (only when matched),
   `Access-Control-Allow-Methods: POST, OPTIONS`,
   `Access-Control-Allow-Headers: Content-Type`,
   `Access-Control-Max-Age: 86400`, `Vary: Origin`, then `exit`.
3. If `Origin` header present: must exactly match an allowlist entry →
   echo it in `Access-Control-Allow-Origin` + `Vary: Origin` and return.
   Mismatch → `403 {"ok":false,"error":{"code":"origin_forbidden"}}`, exit.
4. If `Origin` missing (explicit case, not fall-through): if `Referer` is
   present and its scheme+host prefix matches an allowlist entry, allow
   (no CORS header needed — it wasn't a CORS request). If both are
   missing → `403 origin_forbidden`. (Browsers always send `Origin` on
   cross-origin and same-origin POSTs; this branch only affects curl and
   the dev harness, which sets `Origin` explicitly.)
5. **Never** emit `*`, never emit `Access-Control-Allow-Credentials`.

### C1.2 `POST /api/jd-generate.php`

The client fires **three parallel** requests, one per slot. The client
mints one `client_ref` (UUID v4 via `crypto.randomUUID()`, supported at
the iOS 16 floor) shared by both requests, and persists it via `JD_store`
**before** dispatching either fetch — this is the recoverability handle
required by APP §4.11 (PHP on Bluehost cannot stream partial JSON, so the
client-minted ref, not a server-returned id, is what survives a killed
request).

**Request JSON:**

```json
{
  "client_ref": "8b0d5c1e-…-uuid-v4",       // required, 36 chars, UUID shape
  "slot": "a",                              // required, "a" | "b" | "c" | "d"
  "prompt": "a brass fish that is also a whistle",  // required, 1–500 chars after trim
  "client": "web",                          // "web" | "ios" | "android"; default "web"
  "consent": { "version": "jd-consent-4" }, // required, must equal JD_CONSENT_VERSION
  "website": ""                             // honeypot: must be absent or empty string
}
```

**Server processing order** (each step exits on failure):

1. Origin check (C1.1); method check; JSON parse (`400 bad_request` on
   malformed body or bad `client_ref`/`slot` shape).
2. Honeypot: `website` present and non-empty → `400 bad_request`. No row
   written, no provider called.
3. Prompt: trim for validation; trimmed length must be 1–500 chars
   (`mb_strlen`) → else `400 prompt_invalid`. **Stored byte-exact as
   received** (untrimmed) — the prompt is frozen verbatim.
4. Consent: `consent.version` must equal the server-side constant
   `JD_CONSENT_VERSION` (`'jd-consent-4'`, in `api/jd-config.php`) →
   else `400 consent_required`. (The client always sends it; the modal
   cannot submit without the recorded consent state — C5.2.)
5. `client`: validated against `['web','ios','android']`; anything else
   (or absent) silently becomes `'web'`. Never sniffed from User-Agent.
6. **Submission resolve (race-safe):** `SELECT` `jd_submissions` by
   `client_ref`. If none: rate-limit checks (step 7), then
   `INSERT IGNORE` a new row with `id = jd_ulid()`,
   `pair_order = random_int(0,23)` (a `JD_DRAW_PERMS` index), prompt, `visitor_hash`
   (`msky_visitor_hash($secrets)`), `client`, `ai_consent_at = now`,
   `ai_consent_version`, `status='pending'`; then re-`SELECT` by
   `client_ref` (the unique key makes the parallel-slot race converge on
   one row — the loser's INSERT is ignored). If the resolved row's
   `visitor_hash` differs from the caller's, still proceed (UTC-midnight
   hash rotation mid-flow is legitimate).
7. **Rate limits** (only when creating a new submission; all slot calls
   share one submission so the submission is the rate-limit unit):
   - `COUNT(*) jd_submissions WHERE visitor_hash=? AND created >= now-1h`
     `>= 3` → `429 rate_limited`, `retry_after` = seconds until the
     oldest of those rows ages out (or `3600` if simpler — pick 3600,
     constant). Header `Retry-After` set to the same value.
   - `COUNT(*) … AND created >= <UTC midnight>` `>= 10` →
     `429 rate_limited`, `retry_after` = seconds to UTC midnight.
   - Global circuit breaker: `COUNT(*) jd_generations WHERE created >=
     <UTC midnight>` `>= 100` → `503 drawer_resting`, `retry_after` =
     seconds to UTC midnight. (Counts pending rows too — in-flight
     generations occupy budget.)
   These limits are constants `JD_LIMIT_HOURLY=3`, `JD_LIMIT_DAILY=10`,
   `JD_LIMIT_GLOBAL_DAILY=100` in `api/jd-config.php`.
8. **Slot idempotency:** `SELECT jd_generations WHERE submission_id=? AND
   slot=?`. If a row exists: `status='ok'` → return the stored success
   response again (this IS the recovery path — a retried fetch with the
   same `client_ref`+`slot` is free); `status='pending'` →
   `409 {"error":{"code":"slot_in_progress"}}`; `status='failed'|'rejected'`
   → re-return the stored failure (same shape as step 11/12; **no
   re-generation in v1** — a failed slot stays failed, bounding cost).
9. **Model routing:** `JD_DRAW_PERMS[pair_order]` (C4) maps each slot to
   its `JD_MODEL_POOL` entry. INSERT the `jd_generations` row
   (`status='pending'`, model fields, `harness`, `params` JSON) **before**
   the provider call, then call the provider (C4) with a 90 s cURL
   timeout. In `JD_DEV_MODE` the provider call is
   `jd_mock_call(...)` (C6) — everything else identical.
10. **Extraction:** find the first `<svg` (case-insensitive) through the
    last `</svg>` in the response text. Nothing found → UPDATE row
    `status='rejected'`, `reject_reason='no_svg_found'`, raw kept →
    `422 {"ok":false,…,"error":{"code":"sanitizer_rejected"}}`. If
    stripping was needed (extracted ≠ trimmed full text) set
    `disobedience=1`.
11. **Sanitize** (C3). Reject → UPDATE `status='rejected'`,
    `reject_reason=<enum>`, `raw_response` kept, `svg` NULL →
    `422 sanitizer_rejected`. (The specific reject_reason is stored,
    **never returned to the client** — it could aid probing.)
12. Provider/cURL failure (non-200, timeout, transport error) → UPDATE
    `status='failed'`, raw kept (or the error text) →
    `502 {"ok":false,…,"error":{"code":"provider_failed"}}`.
13. Success → UPDATE row: `svg`, `status='ok'`, `disobedience`,
    `latency_ms`, `usage_tokens`; UPDATE submission `status='generated'`
    (idempotent). Respond `200`.

**Success response (200):**

```json
{
  "ok": true,
  "submission_id": "01J4X6…ULID",
  "gen_id": "01J4X6…ULID",
  "slot": "a",
  "svg": "<svg xmlns=…>…</svg>"
}
```

**No model identity anywhere in this response** — not the model, not the
provider, not the reject reason. Blindness is server-enforced: identity
exists only in the DB until the C1.3 reveal.

**Error envelope (all endpoints):**

```json
{
  "ok": false,
  "submission_id": "01J4…",      // when one exists by that point, else omitted
  "gen_id": "01J4…",             // when one exists, else omitted
  "slot": "a",                   // jd-generate only
  "error": { "code": "provider_failed", "message": "short human-neutral text" },
  "retry_after": 3600            // only rate_limited / drawer_resting
}
```

**Status-code map (jd-generate):** `200` ok · `400`
`bad_request|prompt_invalid|consent_required` · `403 origin_forbidden` ·
`405 method_not_allowed` · `409 slot_in_progress` · `422
sanitizer_rejected` · `429 rate_limited` · `502 provider_failed` · `503
drawer_resting` · `500 server_error` (DB down etc.). The client keys on
`error.code`, not the HTTP status.

### C1.3 `POST /api/jd-rate.php`

One call per submission, at the end of the rate+compare flow. This is
the **only** place model identity is ever released (blind rating is a
server guarantee, not a UI courtesy).

**Request JSON:**

```json
{
  "submission_id": "01J4X6…",
  "client": "web",
  "ratings": [
    { "gen_id": "01J…A", "kind": "grade", "value": 4.0 },
    { "gen_id": "01J…A", "kind": "axis", "axis_id": "restraint",
      "value": 2.0, "note": "added a hat nobody asked for" },
    { "gen_id": "01J…B", "kind": "grade", "value": 3.0 },
    { "gen_id": "01J…B", "kind": "flag",
      "note": "response is broken or offensive (optional note)" }
  ],
  "comparison": { "winner": "a", "strength": "decisive" },
  "ranking": [
    { "slot": "c", "rank": 1 },
    { "slot": "a", "rank": 2 },
    { "slot": "b", "rank": 2 },
    { "slot": "d", "rank": 3 }
  ]
}
```

- `ratings` may be empty (`[]`) — a visitor who rates nothing but picks
  a winner still produced the core datum. Max 64 entries.
- `kind='grade'`: no `axis_id`; `value` must equal a `rank` from
  `taxonomy.grades`. At most one grade per `gen_id`.
- `kind='axis'`: `axis_id` must be a **non-defunct** axis id in
  `taxonomy.axes`; `value` must equal a `rank` of that axis's values.
  At most one per (`gen_id`, `axis_id`).
- `kind='flag'`: no `axis_id`, no `value` (NULL); `note` optional. This
  is APP §4.6's report path — one row, no queue, no admin UI.
- `note`: ≤500 chars, stored truncated.
- `comparison.winner`: `"a" | "b" | "c" | "d" | "tie"`, or `"comparison": null`.
  `null` is legal **only** when the submission has exactly one
  `status='ok'` generation (degraded mode); with more than one ok slot a
  comparison object is required (`400 comparison_required`). Winner is
  named **by slot**, never by gen_id — the server maps slot → gen_id, so
  a client can never file a foreign generation as winner.
- `comparison.strength` (added 2026-08-11, the single-bench likert):
  `"decisive" | "slight" | null` — the margin of the call. A `"tie"`
  must not carry one (`400 rating_invalid`). Nullable on a won slot so
  an older cached client that names only a winner still files; the
  shipping client always sends it. Stored in
  `jd_comparisons.strength`; on a database that has not yet run the
  setup script's migration, jd-rate falls back to filing the batch
  without the margin rather than failing it.
- `ranking` (added 2026-08-22, the four-chair era): the FULL order of
  the survivors — one entry per `status='ok'` slot, `{ "slot": …,
  "rank": <int ≥ 1> }`, named **by slot** for the same reason the
  winner is. It supersedes `comparison` as the judgment of record. The
  rules, all enforced server-side (a violation is `400
  ranking_invalid`, and nothing at all is written):
  - one entry per ok slot, every ok slot present exactly once, no
    unknown slots, no non-ok slots, no duplicates;
  - `rank` is a whole number ≥ 1;
  - **exactly one** entry at rank 1 — there is never a tie for first;
  - ranks are **dense**: the distinct ranks used are exactly {1..k}.
    Ties below first are legal and expected (`1,2,2,3` and `1,2,2,2`
    both pass); a gap is not (`1,2,4` fails).

  **Acceptance policy**, which exists so a visitor on a cached copy of
  the old JS keeps working: `ranking` present and valid ⇒ it is the
  answer. `ranking` absent, `comparison` present ⇒ exactly the legacy
  path, unchanged. Both absent with >1 ok slot ⇒ `400
  comparison_required` as before. Both present ⇒ `ranking` is read and
  `comparison` is ignored without error (the old key is not evidence of
  a bug). The client sends `ranking` only when more than one slot
  survived; a well-formed one-entry order on a single-survivor
  submission is nonetheless accepted rather than rejected, because it
  records the same fact and refusing it would throw away the visitor's
  whole rating batch.

**Server processing:**

1. Origin, method, parse (as C1.2 steps 1). `client` validated as C1.2
   step 5. No honeypot here (no cost to protect), no consent re-check
   (recorded on the submission).
2. Load submission by id → `404 not_found` if absent. Load its
   generations.
3. `submission.status = 'rated'` already → `409 already_rated` (one
   rating batch per submission, ever; the response does **not** repeat
   the reveal — abandoned duplicates don't get a second unveil channel).
   No ok generations → `409 nothing_to_rate`.
4. Validate every rating against the **live** `taxonomy.json` read from
   `art/junk-drawer/data.php`'s source file
   (`__DIR__ . '/../art/junk-drawer/taxonomy.json'`): gen_id belongs to
   this submission and is `status='ok'`; kinds/axes/values as above.
   Any violation → `400 rating_invalid` (nothing written — the batch is
   atomic; wrap in a transaction).
5. `taxonomy_version` is stamped **server-side** from the taxonomy file's
   `version` field (currently 9). The client never sends it (its payload
   came from the same file via data.php; the server copy is
   authoritative).
6. UPDATE submission `status='rated'` **first**, guarded (`WHERE id = ?
   AND status <> 'rated'`) — that UPDATE is the serialization point, and
   a `rowCount() !== 1` is `409 already_rated`. Then INSERT rating rows
   (each with `visitor_hash` of the rater, `client`, `rated_at`); INSERT
   one `jd_ranks` row per ok slot when `ranking` was filed (gen id
   resolved from the slot, never from client input); INSERT the
   `jd_comparisons` row whenever either judgment key was accepted —
   `winner_gen_id` = the mapped winner (the rank-1 generation when the
   answer came as a ranking, NULL for a legacy `"tie"`), `strength` NULL
   on a ranking because an order carries no margin. All in one
   transaction.

   The `jd_comparisons` row is written for BOTH shapes on purpose: it
   keeps the win series that predates ranking one continuous table, and
   keeps every existing reader working untouched.

   If `jd_ranks` does not exist yet (the setup script is a manual run and
   a deploy is instant), the rank rows are skipped, the batch still
   commits, and a line goes to the error log — the same bargain
   `jd_comparisons.strength` already makes. Only the missing-table error
   is caught (`jd_missing_table()`, the sibling of `jd_missing_column()`);
   any other failure still rolls the whole batch back. Rating must never
   break because a migration lagged a deploy.
7. Respond with the reveal.

**Success response (200):**

```json
{
  "ok": true,
  "reveal": [
    { "slot": "a", "model_id": "claude-sonnet-5",
      "label": "Claude Sonnet 5", "vendor": "Anthropic" },
    { "slot": "b", "model_id": "gpt-5", "label": "GPT-5", "vendor": "OpenAI" }
  ]
}
```

`label`/`vendor` resolved from the taxonomy `models` registry by
`model_id`; a degraded submission reveals only its surviving slot(s) —
failed slots ARE included with their model identity (the visitor may
fairly learn who failed): entries carry an extra `"status": "ok"|"failed"|"rejected"`.

**Status-code map (jd-rate):** `200` ok · `400
bad_request|rating_invalid|comparison_required|ranking_invalid` · `403 origin_forbidden`
· `404 not_found` · `405` · `409 already_rated|nothing_to_rate` · `500
server_error`.

## C2. DDL — `api/setup-jd-tables.php`

MySQL 5.7+/MariaDB-compatible, InnoDB, utf8mb4, matching the
`setup-page-events-table.php` pattern. `params`/`usage_tokens` are TEXT
holding JSON strings (no JSON column type — MariaDB compat, per master
plan). All ids CHAR(26) app-generated ULIDs — no AUTO_INCREMENT anywhere.

```sql
CREATE TABLE IF NOT EXISTS jd_submissions (
    id                 CHAR(26)     NOT NULL PRIMARY KEY,
    client_ref         CHAR(36)     NOT NULL,
    created            DATETIME     NOT NULL,
    prompt             TEXT         NOT NULL,
    visitor_hash       CHAR(64)     NOT NULL,
    client             VARCHAR(16)  NOT NULL DEFAULT 'web',
    pair_order         TINYINT      NOT NULL,            -- 0-23: JD_DRAW_PERMS index (slot→model permutation of 4)
    ai_consent_at      DATETIME     NULL,                -- APP §4.5
    ai_consent_version VARCHAR(16)  NULL,                -- APP §4.5
    status             ENUM('pending','generated','rated','failed') NOT NULL DEFAULT 'pending',
    UNIQUE KEY uq_client_ref (client_ref),               -- parallel-slot race convergence
    KEY idx_visitor_created (visitor_hash, created),     -- per-visitor rate limits
    KEY idx_created (created)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE IF NOT EXISTS jd_generations (
    id             CHAR(26)     NOT NULL PRIMARY KEY,
    submission_id  CHAR(26)     NOT NULL,
    slot           ENUM('a','b','c') NOT NULL,
    model_id       VARCHAR(64)  NOT NULL,   -- taxonomy models registry id (join key)
    model_version  VARCHAR(64)  NOT NULL,   -- exact API model string sent on the wire
    provider       VARCHAR(32)  NOT NULL,   -- 'anthropic' | 'openai'
    harness        VARCHAR(16)  NOT NULL,   -- 'v3-web.1'
    params         TEXT         NOT NULL,   -- JSON string: what was actually sent (C4)
    raw_response   MEDIUMTEXT   NULL,       -- pre-extraction, ALWAYS kept once received
    svg            MEDIUMTEXT   NULL,       -- post-extraction, post-sanitize; NULL unless status='ok'
    status         ENUM('pending','ok','failed','rejected') NOT NULL DEFAULT 'pending',
    reject_reason  VARCHAR(64)  NULL,       -- C3 enum string; NULL unless rejected
    disobedience   TINYINT      NOT NULL DEFAULT 0,
    latency_ms     INT          NULL,
    usage_tokens   TEXT         NULL,       -- JSON string from provider usage block
    created        DATETIME     NOT NULL,
    UNIQUE KEY uq_submission_slot (submission_id, slot), -- idempotent slot retry
    KEY idx_created (created),                           -- global daily circuit breaker
    CONSTRAINT fk_jdg_submission FOREIGN KEY (submission_id) REFERENCES jd_submissions(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE IF NOT EXISTS jd_ratings (
    id               CHAR(26)      NOT NULL PRIMARY KEY,
    generation_id    CHAR(26)      NOT NULL,
    kind             ENUM('grade','axis','flag') NOT NULL,   -- 'flag' per APP §4.6
    axis_id          VARCHAR(64)   NULL,      -- kind='axis' only
    value            DECIMAL(3,1)  NULL,      -- numeric rank; NULL for kind='flag'
    note             VARCHAR(500)  NULL,
    taxonomy_version INT           NOT NULL,  -- stamped server-side (9 today)
    visitor_hash     CHAR(64)      NOT NULL,  -- the RATER (may differ from submitter across UTC midnight)
    client           VARCHAR(16)   NOT NULL DEFAULT 'web',
    rated_at         DATETIME      NOT NULL,
    KEY idx_generation (generation_id),
    CONSTRAINT fk_jdr_generation FOREIGN KEY (generation_id) REFERENCES jd_generations(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE IF NOT EXISTS jd_comparisons (
    id             CHAR(26)    NOT NULL PRIMARY KEY,
    submission_id  CHAR(26)    NOT NULL,
    winner_gen_id  CHAR(26)    NULL,          -- NULL = explicit tie
    strength       VARCHAR(8)  NULL,          -- 'decisive'|'slight'; NULL on a
                                              -- tie or a pre-likert client
                                              -- (added 2026-08-11)
    visitor_hash   CHAR(64)    NOT NULL,
    client         VARCHAR(16) NOT NULL DEFAULT 'web',
    rated_at       DATETIME    NOT NULL,
    UNIQUE KEY uq_submission (submission_id),
    KEY idx_winner (winner_gen_id),
    CONSTRAINT fk_jdc_submission FOREIGN KEY (submission_id) REFERENCES jd_submissions(id),
    CONSTRAINT fk_jdc_winner FOREIGN KEY (winner_gen_id) REFERENCES jd_generations(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE IF NOT EXISTS jd_ranks (
    id             CHAR(26)    NOT NULL PRIMARY KEY,
    submission_id  CHAR(26)    NOT NULL,
    generation_id  CHAR(26)    NOT NULL,
    rank_pos       TINYINT     NOT NULL,       -- 1 = best; dense (the distinct
                                               -- ranks used are exactly 1..k);
                                               -- ties legal below 1 only
    visitor_hash   CHAR(64)    NOT NULL,
    client         VARCHAR(16) NOT NULL DEFAULT 'web',
    rated_at       DATETIME    NOT NULL,
    UNIQUE KEY uq_submission_generation (submission_id, generation_id),
    KEY idx_submission (submission_id),
    CONSTRAINT fk_jdrk_submission FOREIGN KEY (submission_id) REFERENCES jd_submissions(id),
    CONSTRAINT fk_jdrk_generation FOREIGN KEY (generation_id) REFERENCES jd_generations(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

`jd_ranks` (added 2026-08-22) is the full order behind each judgment;
`jd_comparisons` keeps its rank-1 winner alongside it. **The column is
`rank_pos`, never `rank`** — `RANK` is a reserved word in MySQL 8.0 (the
window function) and an unquoted `rank` column is a syntax error there.
Do not "tidy" that name, quoted or otherwise. Being a new TABLE rather
than a new column, it needs no ALTER: the `CREATE TABLE IF NOT EXISTS`
above is itself the migration, and `setup-jd-tables.php` reports whether
it landed.

Notes binding on BE-C: the rate-limit queries must use
`idx_visitor_created` and `idx_created` shapes exactly as in C1.2 step 7;
`raw_response` is written the moment the provider answers, before any
verdict; nothing ever UPDATEs a row from `ok` back to anything else.

## C3. Runtime SVG sanitizer — `api/jd-svg-sanitizer.php`

A pure function, no side effects, no globals, testable from the CLI:

```php
function jd_sanitize_svg(string $svg): array
// returns ['ok' => true,  'svg' => <the input, byte-identical>]
//      or ['ok' => false, 'reason' => <enum string below>]
```

**REJECT, never repair.** The function never modifies the SVG: it either
passes the input through byte-identical or rejects it with a reason.
(Repair creates parser-differential bugs; the whole design rests on
this.)

### C3.1 Processing order

1. **Size cap**: `strlen($svg) > 300 * 1024` → `too_large`.
2. **Pre-parse scans** (on the raw string, before DOM):
   `<!DOCTYPE` or `<!ENTITY` anywhere (case-insensitive) →
   `doctype_forbidden`. (No DTDs, no entities, ever — closes XXE and
   entity-expansion regardless of parser flags.)
3. **XML parse**: `DOMDocument->loadXML($svg, LIBXML_NONET |
   LIBXML_NOERROR | LIBXML_NOWARNING)` with
   `libxml_set_external_entity_loader(fn() => null)` installed (defense
   in depth behind step 2; never set `LIBXML_NOENT`). Parse failure →
   `parse_error`.
4. **Root check**: documentElement localName exactly `svg` AND namespace
   URI `http://www.w3.org/2000/svg` → else `bad_root`. Root missing a
   `viewBox` attribute → `no_viewbox`.
5. **Walk every element node** (depth-first over the whole tree),
   applying C3.2–C3.4. First violation wins; return its reason.
6. Pass → return the original string untouched.

### C3.2 Element ALLOWLIST (localName, case-sensitive; namespace must be SVG)

```
Structure:   svg  g  defs  symbol  use  title  desc  switch
Shapes:      path  rect  circle  ellipse  line  polyline  polygon
Text:        text  tspan  textPath
Paint:       linearGradient  radialGradient  stop  pattern
Clip/mask:   clipPath  mask
Markers:     marker
Style:       style                      (text content scanned — C3.4)
Filters:     filter  feBlend  feColorMatrix  feComponentTransfer
             feComposite  feConvolveMatrix  feDiffuseLighting
             feDisplacementMap  feDistantLight  feDropShadow  feFlood
             feFuncA  feFuncB  feFuncG  feFuncR  feGaussianBlur  feMerge
             feMergeNode  feMorphology  feOffset  fePointLight
             feSpecularLighting  feSpotLight  feTile  feTurbulence
SMIL:        animate  animateTransform  animateMotion  mpath  set
```

Any other element → `element_not_allowed`. **Deliberately excluded**
(never add without a new contracts revision): `script`, `foreignObject`,
`image`, `feImage` (fetches its href), `a`, `view`, `metadata`,
`animation`, `audio`, `video`, `iframe`, `handler`, and every non-SVG
element. Any element in a namespace other than
`http://www.w3.org/2000/svg` → `foreign_namespace` (this is what makes
HTML smuggling and `foreignObject`-content games structurally
impossible).

### C3.3 Attribute rules (every attribute of every element)

Checked in this order; first hit rejects:

1. Attribute local name starts with `on` (case-insensitive: `onclick`,
   `onLoad`, …) → `event_handler`.
2. `href` / `xlink:href` (any namespace): value must match
   `/^#[^#\s]+$/` — a same-document fragment only. Anything else
   (external URL, protocol-relative `//`, `data:`, `javascript:`, empty)
   → `external_ref`.
3. Any attribute value containing `url(`: every occurrence must be
   `url(#…)` or `url('#…')` / `url("#…")` (same-document) → else
   `external_url`.
4. Any attribute value matching
   `/(?:javascript|vbscript|data|file|https?|ftp)\s*:/i` — except when
   the whole value is a plain color/number/path — practical rule: apply
   the regex `/(javascript|vbscript)\s*:/i` to all values →
   `dangerous_uri`; and apply `/(?:https?:|data:|\/\/)/i` to values of
   attributes in {`href`,`xlink:href`,`src`,`style`,`values`,`from`,
   `to`,`by`} → `external_url`. (Presentation attributes like `d`,
   `points`, `fill="#aabbcc"` can't smuggle a fetch without `url(` —
   already covered by rule 3.)
5. `style` attribute: scanned with the C3.4 rules → `style_external`.
6. SMIL guard: on `animate`/`set`/`animateTransform`/`animateMotion`, an
   `attributeName` of `href` or `xlink:href` → `animated_href` (blocks
   animating a safe href into an unsafe one). `mpath` href follows
   rule 2.

### C3.4 `<style>` element text and `style` attribute values

Case-insensitive scans of the raw CSS text:

- `@import` → `style_external`.
- every `url(` occurrence must be immediately followed by `#`, `'#`, or
  `"#` → else `style_external` (kills remote fonts, raster `data:` URIs,
  protocol-relative fetches inside CSS).
- `expression(` → `style_external`.
- `data:` anywhere in style text → `style_external`.

### C3.5 Rejection-reason enum (stable strings, stored in `jd_generations.reject_reason`)

```
too_large  doctype_forbidden  parse_error  bad_root  no_viewbox
foreign_namespace  element_not_allowed  event_handler  external_ref
external_url  dangerous_uri  style_external  animated_href  no_svg_found
```

(`no_svg_found` is set by the extraction step in jd-generate, not by the
sanitizer, but lives in the same enum/column.) These strings are frozen —
the eval export depends on them. Never returned to clients.

### C3.6 Test harness — `scripts/test-jd-sanitizer.php` + `scripts/jd-sanitizer-fixtures/`

Runnable in the CI container: `php scripts/test-jd-sanitizer.php` → prints
one line per fixture, exits 0 iff all pass. Fixture filenames encode the
expectation: `ok-<name>.svg` must pass; `reject-<reason>-<name>.svg` must
be rejected with exactly `<reason>`. BE-C ships at minimum: 3 `ok-`
fixtures (plain shapes; gradients+filter; SMIL animation) and one
fixture per rejection reason (14). BE-K's adversarial pass adds fixtures
(nested CDATA, entity tricks, `xlink:href` obfuscation, style `url()`
games, case/namespace games) — every bypass attempt becomes a permanent
fixture, pass or fail.

### C4.3 Request parameters (per provider)

**Anthropic** (`https://api.anthropic.com/v1/messages`, headers

`Content-Type: application/json` — the api/chat.php pattern):


**OpenAI** (`https://api.openai.com/v1/chat/completions`, header

**Kimi** (`https://api.moonshot.ai/v1/chat/completions`, header

**Google** (`https://generativelanguage.googleapis.com/v1beta/models/
<api_model>:generateContent`, header `x-goog-api-key: <key>`):

`{"max_tokens":12000,"thinking":"disabled","temperature":"provider-default"}`

### C5.4 Modal state machine

One modal, matching `JD_record`'s conventions exactly: scrim + card,
`role="dialog" aria-modal="true"`, focus trapped (Tab cycles inside;
focus returns to the button on close), Esc and scrim-click close the top
layer only — and since the record card already owns a global Escape
handler with layer-peeling, the turn modal registers its handler the
same way and **never both open at once** (opening the turn modal is a
no-op while the record card is open, and vice versa).

States (`jd-turn-v1.state`):

```
consent → prompt → generating → reveal → rate → compare → unveil → (closed)
                       │            └───────────── degraded path ──────┐
                       └ failed-both → apology → (closed)              │
   degraded: exactly one slot ok → reveal-one → rate → unveil (no compare)
```

1. **consent** — entered only when `jd-consent-v1` absent/version-stale
   (C5.2). Otherwise skipped.
2. **prompt** — textarea, live char counter (`aria-live="polite"`),
   submit disabled while empty/over 500. Honeypot: a visually-hidden
   (`position:absolute; left:-9999px`, NOT `display:none`) text input
   named `website`, `tabindex="-1"`, `autocomplete="off"`, sent in the
   body. Rate-limit / resting errors from a previous attempt render
   here as honest copy ("the drawer is resting — come back tomorrow"),
   with `retry_after` humanized.
3. **generating** — on submit: mint `client_ref`, write `jd-turn-v1`,
   THEN dispatch both fetches in parallel (slot a, slot b). Painterly
   progress ("two machines are drawing…"), per-slot arrival
   indicators. **No client-side abort/timeout on these fetches** — the
   server owns the 90 s budget; the UI shows elapsed reassurance copy
   past ~60 s. Per-slot settle updates `jd-turn-v1.slots`.
   - both ok → **reveal**
   - one ok, one failed/rejected → **reveal** (degraded: one plate + a
     quiet "the other machine's drawing didn't survive" note)
   - both failed → **apology** ("both machines failed; this cost you
     nothing" — true: the rate limit counts submissions, but be honest
     that the day's global budget was touched only if 503).
   - 429/503 before submission existed → back to **prompt** with the
     message.
4. **reveal** — SVG(s) inlined **only after `JD_svgInst` id-namespacing**
   with fresh prefixes (`jua<n>_` / `jub<n>_`) — same discipline as
   curated items, non-negotiable (APP §4.12). Labeled only "A" and "B";
   nothing in the DOM, storage, or network hints at model identity.
   Mobile: stacked with A/B tabs per PLAN-MOBILE's sheet conventions.
5. **rate** — the survey instrument per response, rendered **from the
   already-fetched `payloadRef.taxonomy`** (the pile loader hands the
   payload over; if somehow absent, re-fetch data.php via JD_API): the
   full grade scale as pills (label + description, ranks as values),
   then each **non-defunct** axis (`axis.defunct` skipped) with its
   value pills + a "skip" option + optional note field. Values held as
   the numeric `rank`s — no id/label strings ever leave the client.
   Everything skippable. Plus one unobtrusive flag control per response:
   "this response is broken or offensive" checkbox + optional note →
   a `kind:'flag'` rating row (APP §4.6). No size picker, no pin.
6. **compare** — the visitor's judgment: with four chairs drawing every
   turn this is now a full ORDER of the survivors, not a single pick,
   and it goes up as C1.3's `ranking` (exactly one first place; ties
   allowed below it). Required whenever more than one slot survived. On
   submit: build the C1.3 body from held state, POST jd-rate. Degraded
   path skips this state; jd-rate is sent from **rate**'s "done" with
   no judgment key. (The A/B/tie `comparison` this state used to send
   is still accepted by the server forever — that is what a visitor on
   a cached copy of the old JS is holding. FE owns the widget; the wire
   shape is C1.3's.)
7. **unveil** — render `reveal[]` ("A was Claude Sonnet 5; B was
   GPT-5"), then place the winner: if winner `a`/`b`, that generation;
   if `tie`, ask the visitor "keep one?" (A / B / neither) — a purely
   local choice, not recorded server-side. Degraded: the surviving
   generation is the placed item. Placement: append to
   `jd-user-items-v1` (evict >5), add a scatter position for it into the
   `jd-scatter-v2` map, and insert into `.jd-pile` as a `.jd-item
   jd-item--visitor` with sizeClass `m` (visitor items are always
   filed "m"; the standard id-hashed jitter applies), inlined via
   `JD_svgInst` (`juw<n>_` prefix), **visually tagged as a visitor
   item** (paper-tag treatment, `jd-item--visitor` class — final art
   FE-C's call within the mockup-5 hardware language). The item joins
   the existing drag/rotate machinery by being a standard `.jd-item` —
   it must not need any special-casing in the gesture code; if it does,
   the integration is wrong. Clear `jd-turn-v1`. Close returns focus to
   the button.
8. **Page load restore**: on init, read `jd-user-items-v1` and re-place
   stored visitor items into the pile (same path as step 7's placement,
   reusing stored scatter positions). `jd-turn-v1` found on load (a
   turn abandoned mid-generating in a *previous* page life) → v1
   discards it silently (the reserved C1.4 endpoint is the future
   recovery path).

**Abandonment:** closing (Esc/scrim/close button) from `consent`,
`prompt`, `unveil`, `apology` → immediate close. From `generating`,
`reveal`, `rate`, `compare` → one confirm layer ("abandon this turn?");
on confirm, close and clear `jd-turn-v1`; in-flight fetches are NOT
aborted (the server completes and records the generations — an
unrated `generated` submission is itself the abandonment datum; no
jd-rate call is ever sent for it).

### C6.1 The gate — in `api/jd-config.php`

```php
define('JD_IS_PRODUCTION', is_readable('/home1/tdrivemy/private_config/secrets.php'));
define('JD_DEV_MODE', !JD_IS_PRODUCTION && getenv('JD_DEV_MOCK') === '1');
```

Why this cannot trigger on production: (a) the production secrets file
**exists by definition on Bluehost** — database.php and chat.php load it
on every request; if it were missing the whole site is already down, so
`JD_IS_PRODUCTION` is true there and the `&&` short-circuits before the
env var is even consulted; (b) the second condition is an explicit
opt-in env var that shared hosting visitors cannot set and the owner
never sets in Apache config. Both independent conditions must fail
simultaneously. Dev mode is **default-off even in the container** — QA
runs `JD_DEV_MOCK=1 php -S localhost:8000 router.php`.

`api/jd-config.php` also owns `jd_db()`: production/local-with-MySQL →
`require database.php`, return `$pdo`; `JD_DEV_MODE` → return a
`PDO('sqlite:' . <repo>/local-dev/jd-dev.sqlite)` (created on demand,
`PRAGMA foreign_keys = ON`). All endpoint SQL is written to run on both
(no MySQL-only functions in queries; date math done in PHP, passed as
bound parameters — e.g. the rate-limit cutoffs are computed with
`gmdate()` in PHP, never `NOW() - INTERVAL`).

### C6.2 SQLite DDL deltas (in setup-jd-tables.php's dev branch)

Same tables/columns/indexes as C2 with exactly these mechanical deltas:
`ENUM(…)` → `TEXT CHECK (col IN (…))`; drop `ENGINE/CHARSET/COLLATE`
clauses; `MEDIUMTEXT` → `TEXT`; `DATETIME` → `TEXT` (ISO strings —
already what PHP writes); `TINYINT` → `INTEGER`. Nothing else differs —
ids are app-generated so no AUTO_INCREMENT translation is needed.

### C6.3 Canned providers — `api/jd-mock-provider.php`

Included **only** when `JD_DEV_MODE`; exposes
`jd_mock_call(string $provider, string $prompt): array` returning the
exact shape of the real call
(`['ok'=>bool,'http_code'=>int,'raw'=>string,'usage'=>array,'error'=>?string]`),
so jd-generate's post-call path (extraction → sanitizer → storage) is
**identical in both modes** — the mock replaces only the cURL exec.

- Fixture SVGs in `local-dev/jd-mock/`: `mock-anthropic.svg` (warm
  palette, distinct look) and `mock-openai.svg` (cool palette) — keyed
  by provider, so the blind-reveal flow is genuinely exercised (slot
  randomization still happens; QA can verify blindness by look).
- Artificial latency: `usleep(1000 * (int)(getenv('JD_DEV_LATENCY_MS') ?: 1200))`;
  set `JD_DEV_LATENCY_MS=45000` to rehearse the long-wait UI.
- **Magic prompt tokens** (case-insensitive substring of the prompt):
  - `[fail]` → both providers fail; `[fail:anthropic]` / `[fail:openai]`
    → that provider returns `ok=false` (simulated timeout) →
    exercises `provider_failed` and the degraded/both-failed UI states.
  - `[hostile]` / `[hostile:anthropic]` / `[hostile:openai]` → returns
    `local-dev/jd-mock/mock-hostile.svg` (contains `<script>`, an
    `onclick`, and an external `<image href>`) — which then flows
    through the **real** sanitizer and exercises the rejection path
    end-to-end (`sanitizer_rejected` in the UI, `rejected` row +
    `reject_reason` in the DB).
  - `[prose]` → wraps the fixture in code fences + chatter → exercises
    extraction + `disobedience=1`.
- Mock usage numbers are fixed constants (nonzero, so the export has
  shape).

### C6.4 `setup-jd-tables.php` behavior per environment

- **Dev (`JD_DEV_MODE`)**: creates the SQLite file + schema (C6.2),
  prints per-table results. Rerunnable (`IF NOT EXISTS`).
- **Local-with-MySQL** (config/secrets.php exists, dev mode off): runs
  the C2 MySQL DDL against database.php's `$pdo`, no key required.
- **Production**: requires `?key=<value>` matching
  `$secrets['jd_setup_key']`; if the secret is unset or the key
  mismatches → `403` with a one-line instruction ("add jd_setup_key to
  private_config/secrets.php"). Header comment carries the existing
  setup-script convention verbatim: "One-time setup script — delete
  after running." (Pattern: `setup-page-events-table.php`, upgraded
  with the key gate because this one creates four tables.)

QA's loop: `JD_DEV_MOCK=1 php -S localhost:8000 router.php` → run
setup → Playwright drives consent → prompt → generating → reveal →
rate → compare → unveil → item in pile; then the three magic-token
scenarios; then `php scripts/test-jd-sanitizer.php`.

## Amendments (post-review, 2026-08-09)

Both critic reviews of the shipped implementation passed with ADVISORY
findings only. The findings below were adjudicated **ACCEPTED AS IS** —
they are recorded here so a future reader does not re-litigate them as
oversights. (The findings that were fixed in code are not listed; they
are in the diff.)

- **(a) Rate-limit COUNT-then-INSERT TOCTOU** (C1.2 step 7). Two
  concurrent submissions can both read a count under the limit and both
  insert. Accepted for v1: the measured overshoot is small and bounded —
  it costs at most one extra submission per racing pair, and it is
  bounded the same way in both windows (the per-visitor hourly/daily
  counts and the global `JD_LIMIT_GLOBAL_DAILY` breaker), so the day's
  spend cannot run away. A transaction or a counter table is the fix if
  abuse is ever observed; until then it is not worth the write contention
  on shared hosting. Revisit only on evidence.
- **(b) A passing `<style>` element is a document stylesheet** (C3.2 /
  C3.4). The sanitizer permits `<style>`, and the SVG is inlined into the
  page, so sanitizer-legal CSS can restyle the visitor's own view of the
  drawer. Accepted for v1: this is self-defacement and nothing more —
  C3.4 already denies every fetch (`@import`, `url()`, `image-set()`,
  `cross-fade()`, bare-string and protocol-relative URLs, backslash
  escapes), no script can execute, the effect is display-only, and it is
  session-local to the one visitor who commissioned it (visitor items are
  never shown to anyone else — see Deferred). Dropping `<style>` would
  cost real drawings their styling for no attacker gain.
- **(c) Mobile reveal ships stacked WITHOUT A/B tabs** — an approved
  deviation from C5.4 step 4, which specified "stacked with A/B tabs".
  The whole question the state asks is "which of these two", and a tab
  that hides one of them asks the visitor to hold it in their head; the
  side-by-side comparison works better stacked. The CSS says so at
  `@media (max-width: 600px)`.
- **(d) `xml:base` — closed in code**, not accepted. It is now in
  `JD_SVG_REF_ATTRS`, so C3.3 rule 4 runs on it and an absolute or
  protocol-relative base is rejected `external_url`; regression fixture
  `reject-external_url-xml-base.svg`. Listed here only because it was
  raised alongside (b).
- **(e) Stranded `pending` rows have no reaper, by design in v1.** A
  fatal mid-generation (OOM, timeout kill) leaves a `jd_generations` row
  at `status='pending'` forever: it counts against the daily budget until
  UTC midnight rolls the window, and its slot answers `409
  slot_in_progress` to any retry (C1.2 step 8). No cron, no sweeper — the
  owner clears it by hand. See the "Clearing a wedged day" note in
  PLAN-USER-PROMPTS.md §7.
- **(f) C5.5 "The button" is SUPERSEDED (2026-08-10)** by the in-pile turn
  object specified in PLAN-TURN-OBJECT (owner picked candidate 8e, the
  doorbell). The corner brass card-holder — its `index.php` markup, its
  `.jd-turn-btn` CSS and its JS wiring — is retired, and with it every
  geometry rule C5.5 wrote about the stage's front band. What C5.5 still
  binds is carried over unchanged by the pile object: a real button to the
  accessibility tree (`role="button"`, focusable, Enter/Space, visible focus
  ring, `aria-haspopup="dialog"`), labelled from `JD_STRINGS.turnButton`, a
  ≥44 px hit target at every viewport — held now by an unconditional
  `min-width` floor on the object rather than the button's old `min-height:
  max(44px, …)`, because the pile's cqmin sizing collapses on a short well
  (a phone in landscape is wider than the 768 px small-well breakpoint and
  drew the plate at 32.5 px before the floor) — and no interference with pile drags
  (it IS a pile item now, so it shares their gesture path rather than
  dodging it). Everything else in C5 — the modal, the state machine, the
  endpoints, consent, persistence — is untouched by that change.
